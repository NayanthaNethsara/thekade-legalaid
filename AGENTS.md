# Engineering Guidelines

Conventions for all code written and all responses given in this repository.

## 1. Self-Documenting Naming

Code should be readable without external explanation.

- **Variables**: use specific, descriptive nouns that reflect the data's purpose or units.
- **Functions**: use clear verb-noun combinations that describe the action and its result.
- **Booleans**: use prefixes such as `is`, `has`, or `can` so conditionals read like English sentences.

## 2. Strategic Commenting

Treat a comment as a sign that the logic may be too complex.

- **Avoid redundancy**: do not explain what the code is doing when it is already clear from the syntax.
- **Focus on intent**: comment the "why" behind a non-obvious decision, a technical constraint, or a business requirement.
- **Refactor first**: before adding a comment, see if the logic can be simplified or moved into a better-named helper function.

## 3. Presentation and Structure

- **Conciseness**: give direct, technical explanations without conversational filler.
- **Formatting**: use standard Markdown headers and lists to maintain a clean visual hierarchy.
- **No emojis**: keep interfaces, code, and responses purely text-based and professional.
